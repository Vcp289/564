BUG REPRODUCED FROM USER SCREENSHOT
- After iOS/PWA swipe-kill and reopen on History, Actual rows returned (e.g. 26 Aug / 25 Aug),
  but P18 / P19 / X3 columns could show “—” while CLS / GL / AIL were already available.
- This was not an engine-accuracy problem. It was a cold-boot persistence layering bug.

ROOT CAUSE
1) V7.20.86l intentionally restored the compact synchronous History journal before first History paint.
2) That compact journal stores Profiles + actualDraws only; dailyTables and records are intentionally empty.
3) loadState() could also merge that newer compact journal over healthy MAIN using mergeRecoveredHistory().
4) mergeRecoveredHistory() treated the journal's intentional empty dailyTables/records as authoritative,
   which removed the derived baseline needed by P18/P19/X3 fingerprints after a swipe/kill.
5) V7.20.86l then cleared performance caches before History render, so the three pattern engines had
   no valid synchronous adapter left and displayed pending/“—”.

PRO FIX
A) Full-state History first paint
- History cold boot now parses the durable MAIN state once before first paint.
- The compact source journal is only a recovery overlay / last-resort rescue; it is no longer used as
  the normal standalone History state.
- No clearPerformanceCaches() is called after restoring the synchronous model adapters.

B) Source-only journal merge guard
- Version-2 compact History journal remains small and iOS-safe.
- When it is newer than MAIN, actualDraws/Profile source rows may still win, BUT MAIN dailyTables and
  records are preserved during the merge.
- This keeps derived fingerprints stable without weakening Save durability.

C) Cache-first model restore
- restoreUnifiedAIProfileSync(activeProfile) runs before first History paint.
- X3 IndexedDB durable mirror may hydrate after the stable first paint.
- History never starts a heavy P18/P19/X3 rebuild on the foreground path.
- If no durable generation exists, missing work remains AI-page/background work by design.
