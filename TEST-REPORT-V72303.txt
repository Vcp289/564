LuckyNumber V7.23.04 — Hybrid Status Normalized Pro E2E Test
Date: 2026-08-29

ROOT CAUSE FIXED
1. Production engines use "notfound" for a verified miss.
2. The new canonical store accepted only "miss", so "notfound" was incorrectly normalized to "pending".
3. This made miss-heavy P18/CLS/GL/AIL/P19/X3 cells render as em-dash and caused endless repair/rebuild behavior.
4. Canonical normalization now maps notfound -> miss and rev/reverse -> reversed.
5. Natural strict-prior warm-up pending rows are no longer treated as repair failures.

HYBRID ARCHITECTURE
- Actual result saves immediately.
- WF is completed incrementally/serialized.
- Initial migration builds P19/X3 once and persists selector checkpoint.
- Normal latest Save evaluates only the new row for P18/P19/X3; no whole-profile P19/X3 rebuild.
- Canonical History/Analysis store keeps verified old rows and merges only missing/new values.
- Heavy deterministic ranking audit is removed from the Save completion path; fast trusted ranking authority is used immediately.

V7.23.04 DIRECT SOURCE HISTORY / ANALYSIS FIX
Root cause found in V7.23.02:
- history-analysis-core overrides readCommittedAIHistorySnapshot() with the new canonical snapshot.
- A fresh/partially migrated canonical store therefore returned a valid snapshot object containing mostly pending rows.
- Analysis treated that object as an exact committed generation, so the old snapshot fallback was never used.
- Result: History could show em-dashes while Analysis evaluated only a few Profile-Draw rows (example reported: 4).

Fix:
- Added LNCanonicalHistory.ensureRows(): synchronous, bounded, read-only/direct-source status bridge.
- It uses existing History strict prior-only/display status resolvers and durable P18/P19/X3 adapters only.
- It does NOT train, rebuild WF, or use a target result as prediction input.
- History first paint primes only the newest 12 rows so visible rows do not collapse to all dashes.
- Analysis primes only rows inside its selected 7/14/30/60/90/180 window before reading the canonical snapshot.
- Heavy self-heal remains background-only for statuses that genuinely cannot yet be derived.
- Canonical durable store key remains v72302 intentionally, so upgrading does not erase already normalized data.
